# Lockfile Safety

**When to load this:** Before running `npm install` for any reason, or before touching `package.json`.

## Overview

This repository has zero dependencies as a hard invariant, but `npm install`'s default behavior — generating `package-lock.json` even with an empty dependency tree — combined with a `.gitignore` that does *not* exclude that file, creates a compounding failure surface. `README.md` itself documents the wrong command. This module exists so lockfile generation is caught before it ever reaches a git stage, not after.

## Key Files

- `package.json` — zero `dependencies`/`devDependencies` keys; 5 frozen scripts (`package.json:6-12`).
- `.gitignore` — 8 deliberate entries, confirmed to contain no `package-lock.json` entry.
- `README.md` — instructs bare `npm install` in its Setup section, which contradicts process policy.

## Patterns & Rules

1. **Always run `npm install --no-package-lock`, never bare `npm install`.** Bare `npm install` generates `package-lock.json` even when `dependencies`/`devDependencies` are both empty (GUARDRAILS.md §2 rule 4, §6 trap 4).
2. **`.gitignore` does NOT block `package-lock.json`.** Confirmed by direct read of `.gitignore` (8 entries: `node_modules/`, `dist/`, `.env`, `*.log`, `__pycache__/`, `.DS_Store`, `graphify-out/manifest.json`, `graphify-out/cost.json`) — none of these match a lockfile. Lockfile prevention is enforced entirely by process policy (this rule), not by tooling (GUARDRAILS.md §6 trap 8).
3. **`README.md` shows bare `npm install` in its Setup section — this is known, accepted documentation drift.** GUARDRAILS.md §2 rule 4 explicitly states that this drift "does not authorise using bare `npm install`." Following the README literally is not a valid defense if a lockfile appears.
4. **`package-lock.json` presence is an immediate auto-reject trigger, full stop.** No fix-and-continue — GUARDRAILS.md §5 trigger 3 lists it alongside protected-file modification and added dependencies as a no-fix-attempt rejection.
5. **Zero dependencies is permanent, not a temporary state.** MISSION.md hard invariant #3: no `dependencies` or `devDependencies` entry may ever be added, for testing, linting, formatting, or type-checking purposes. There is no "graduation" path to a build step or transpiler.
6. **If a lockfile is ever generated by accident, delete it before staging anything.** GUARDRAILS.md §6 trap 8 states this explicitly — a lockfile that isn't caught by `.gitignore` will otherwise get silently included in the next `git add`.

## Gotchas

- Running any generic "install dependencies" step from habit (e.g., copy-pasting a setup command from another project) will silently create `package-lock.json` — always use the `--no-package-lock` flag explicitly, every time, even when you're confident no deps will be added.
- `README.md` is the one file automation may freely edit (CLAUDE.md "Important Files" table) — if you're touching setup docs anyway, consider (but do not require) correcting the bare `npm install` instruction to include `--no-package-lock`, since MISSION.md's "Allowed Evolutions" permits README improvements.
- Because `package.json` scripts are a protected/sealed API (GUARDRAILS.md §4), do not attempt to add a `preinstall` or `postinstall` hook to enforce `--no-package-lock` automatically — that would itself be a protected-file violation.
